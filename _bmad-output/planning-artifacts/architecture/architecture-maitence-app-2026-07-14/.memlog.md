- (decision) Paradigm: Event-Driven Serverless Architecture, domain-bounded Lambda services behind a single API Gateway, each domain internally shaped hexagonal (handler/adapter -> application/use-case -> domain -> infra adapter). Named pattern chosen so a builder can infer layering without re-deriving it.
- (decision) AD: Bounded-context list (10): Identity, Intake&Media, AIDiagnosis, Taxonomy&Matching, TrustAndQuality, Verification, JobQueue&Lifecycle, Outcome&Pricing, Billing&Tiering, Notifications. Each owns its own datastore; no domain reads another's table directly.
- (decision) AD: Logical bounded-context boundary is decoupled from physical Lambda-function/stack grouping -- day-1 deploys may co-locate multiple domains behind fewer Lambda functions/stacks for ops simplicity, but data ownership, API contracts, and event contracts stay fixed regardless of how many physical stacks exist. Prevents premature 10-microservice ops burden while keeping the contract clean for later splitting.
- (decision) AD: Single central API Gateway (HTTP API) fronts all domains, Cognito JWT authorizer, route-grouped by domain (/leads, /diagnosis, /contractors, /queue, /verification, /tiers, /outcomes, /media). Both mobile (Swift/Kotlin) and web (Angular) clients call this one gateway. Prevents divergent auth/observability/rate-limit setups per surface.
- (decision) AD: Cross-domain communication is either async via EventBridge custom bus (default, eventual consistency) or a narrow synchronous internal API call for read-only lookups that must be immediately consistent (e.g. Matching checking current Verification status) -- never a direct cross-domain table read.
- (decision) AD: Data store split -- DynamoDB single-table-per-domain for high-write/transactional domains (Intake/Lead, JobQueue/Job, Verification status, Outcome, Notifications); Aurora Serverless PostgreSQL for relationally-shaped reference/join-heavy data (Taxonomy: Trades/Services/ContractorTrades/ContractorServices per addendum's own relational schema; Billing/Tiering). Reason: taxonomy matching is join-heavy and small in volume, DynamoDB access patterns would force denormalized duplication with no benefit; everything else is single-entity-keyed high-throughput access, DynamoDB's native fit.
- (decision) AD: AI Diagnosis pipeline -- synchronous path (photo+description) is a direct Lambda call chain (API GW -> Intake Lambda -> Rekognition -> Bedrock -> persist -> return), target low-seconds per PRD FR-1 NFR. Async path (video) is a Step Functions Standard workflow triggered off a MediaUploaded(video) event, with retry/backoff built into states, publishing AIDiagnosisEnriched on completion. Step Functions chosen over plain SQS+Lambda chaining because the multi-step AI orchestration (extract frames -> Rekognition -> Bedrock -> persist -> notify) benefits from built-in state/retry visibility, not because of raw throughput needs.
- (decision) AD: Anonymous/unauthenticated homeowner session -- UJ-1 requires an unauthenticated homeowner to start a Guided Assessment. Intake issues a short-lived signed session token scoped only to that draft Lead's id (not a full Cognito identity); token is promoted to a full Cognito identity at Booking Confirmation, where contact info is captured. Prevents an anonymous session from ever reading/writing any Lead but its own.
- (decision) AD: Two separate Cognito User Pools -- Homeowner Pool (mobile, lighter auth, optional social login) and Contractor/Admin Pool (web, MFA required, seat-based via Tier). Kept separate because their trust levels, MFA requirements, and account-recovery flows genuinely differ (Contractor is a paying business account with staff seats; Homeowner is throwaway-friendly). Two independently-built auth flows sharing one pool would drift on MFA/seat rules.
- (decision) AD (security, load-bearing): Homeowner contact info (phone/email/address) is stored in a physically separate encrypted attribute-set/table from the rest of the Lead record, redacted from every Contractor-facing read model/API response until a Contact-Reveal transaction fires. The acceptance-transaction Lambda is the ONLY write path permitted to unlock/copy contact fields into the Contractor-visible projection, and it always emits ContactRevealed in the same transaction. Prevents any future Contractor-facing endpoint from accidentally leaking contact info pre-reveal (this is literally what FR-13 depends on).
- (decision) AD: IAM -- one execution role per Lambda function, scoped by resource ARN to only the tables/buckets/downstream services that Lambda actually calls (no shared broad execution role). KMS: customer-managed keys (CMKs), one per domain's datastore, not the AWS-managed default key, so key policy and rotation are explicit and independently auditable per domain.
- (decision) AD: Media upload security -- Homeowner clients never upload directly to a Lambda; they get a short-expiry presigned S3 PUT URL scoped to that Lead's key prefix from Intake. An S3 event triggers a malware/AV scan (GuardDuty Malware Protection for S3 or equivalent) before the object is eligible for the AI Diagnosis pipeline or Rekognition/Bedrock calls -- user-uploaded media is attacker-controllable input reaching AI services and long-term storage, so it is never trusted un-scanned.
- (decision) AD: Edge security -- AWS WAF attached to the API Gateway (rate-based rules, managed core rule set) since Homeowner intake routes are public/unauthenticated-reachable. CloudTrail (org trail, data events on the contact-info and verification tables specifically), GuardDuty, and Security Hub are the baseline account-level security monitoring, not opt-in extras.
- (decision) AD: IaC = AWS CDK (TypeScript) -- matches the locked backend-API language (addendum Tech Stack Direction), one less language for infra maintainers to context-switch into. Verified current: aws-cdk-lib 2.261.0 (2026-07-02).

- (decision) Convention: entity ids are ULIDs (lexicographically sortable, k-sortable by creation time -- useful for DynamoDB partition/sort key ordering of Leads/Jobs by recency) prefixed by type, e.g. lead_01J..., job_01J..., ctr_01J.... - (decision) Convention: every EventBridge event uses one envelope -- {eventId, eventType, occurredAt, source (domain name), correlationId (traces back to originating Lead/Job), version, detail{}}. eventType is PascalCase past-tense (LeadAccepted, ContactRevealed). Every domain that publishes bumps 'version' on breaking detail-shape changes rather than mutating silently, since other domains' Lambdas consume detail{} by shape.
